# eval-pool: השוואת מודלים על המבחנים בלי להטמיע את הספרייה

כדי למדוד מודל חדש על החיפושים האמיתיים, על eval-v1 ועל eval-100, צריך את הצד הסמנטי שלו. בדרך הרגילה מטמיעים את כל
הספרייה, 5.7 מיליון שורות: כארבע שעות ב־Kaggle לתלמיד, ופי 3–4 למורה. כאן מסתפקים במועמדים שכבר יש לכל חיפוש: 150 של
החיפוש הרגיל ו־150 של הצד הסמנטי של האפליקציה, באותו היקף שבו החיפוש רץ. המודל מדרג אותם מחדש, ושאר העמוד נבנה כמו
באפליקציה: RRF, ‏`keepLeaders` וכלל הרמות.

**המגבלה:** שורה שהמודל החדש היה מוצא, ואינה בין המועמדים, לא נספרת. ההשוואה הוגנת בין המודלים, כי כולם מדרגים את אותן
שורות. אבל המספרים אינם בדיוק אלה של האפליקציה עם המודל החדש.

## הצעדים

1. [`pool_spec.py`](pool_spec.py) אוסף מריצות ה־harness את החיפושים ואת המועמדים שלהם. נשמרים רק השאילתות ומזהי השורות,
   בלי טקסט.
2. [`../pool_rank.py`](../pool_rank.py) מטמיע את המועמדים ואת השאילתה בכל מודל, ומדרג לפי קוסינוס. זה נעשה ב־Kaggle:
   `kaggle_run.py push pool --spec pool.json --release v3-20261012193827`. השלב מוריד את הספרייה בגרסה שעליה רצו
   המבחנים, ומדרג במודל הבסיס, במורה, בתלמיד ובמורה אחרי tune, לפי מה שמחובר.
3. [`rerank.py`](rerank.py) מחליף בכל ריצה את הצד הסמנטי בסדר של המודל.
4. **המדידה:** [`../eval-real/level_order.py`](../eval-real/level_order.py) על הריצה החדשה, עם הציונים. שורה שלא
   שופטה ועולה לשלוש הראשונות נשפטת לפני שמשווים.

**בדיקת שפיות:** הדירוג של התלמיד במאגר צריך לתת בערך את מה שהאפליקציה נותנת היום, כי הצד הסמנטי שלה הוא התלמיד.

**תוצאות:** [`results-tune.md`](results-tune.md): הבסיס, המורה, התלמיד והמורה אחרי tune.

## שאלות הפיתוח של האימון

שאלות האימון שלא נכנסות לאימון ([`../train-v2/`](../train-v2/README.md), אצוות 8–9) רצות ב־harness כמו המבחנים, עם שורת
היעד ב־`expected`. ב־`pool_spec.py` הן הריצה בשם `dev`, ושורת היעד נוספת למועמדים שלהן, כדי שכל מודל ידרג אותה.
[`dev_measure.py`](dev_measure.py) מודד באיזה מקום כל מודל שם את שורת היעד: בצד הסמנטי לבד, ובעמוד המשולב של האפליקציה
(RRF במשקל 3).
